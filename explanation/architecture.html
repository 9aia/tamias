Architecture ​

tamias is ports-and-adapters. The engine owns the generic half of distribution; every content meaning is an adapter.

The install path ​

ref ─► resolve ─► (cache hit?) ─► fetch ─► driver install ─► store

include: composes payloads: each entry resolves to a store payload or a recursively-installed ref, overlay() deep-merges bases (earlier includes win, local wins) and the composed tree is what drivers see, what gets digested, and what the store commits. publish/bundle pack flatten includes by default (--keep-includes ships the raw payload).

resolve pins git refs to a commit sha up front, so the content- addressed cache can be hit before fetching. The fetch→unpack split is what makes repeat installs and air-gapped nodes free.

Declared bins[] (P-023) ride the same commit: every install path — install/add/update, sync, the tamias serve install op, the TUI — deploys them into the bin dir by default (--no-bins opts out on the CLI verbs) — shim: cli entries become generated scripts exec'ing tamias bin exec, and payload: tools/bin/<triple>/… entries link real binaries through a per-package bin-alias/ so upgrades don't break them. bin/ payload files link the same way (legacy, undeclared). See Put a package's binaries on your PATH.

Stores ​

  • install store — <tamias-home>/store/<name>@<version>/ with a .tamias-store.json record (source ref, resolved sha, payload digest, installed-at, trust tier).
  • fetch cache — content-addressed; remove never touches it.
  • registry — where published content lives: a directory, or a Cloudflare Worker + R2 + D1/KV.

Provenance ​

verify recomputes the payload digest against the record. Digest-pinned refs (#sha256:…, resolved shas) are the integrity contract — see Security model for the full trust story, including the --allow-drivers consent gate on payload-shipped drivers.

The embedding surface ​

tamias serve (the tamias-serve crate) runs the same install/list/info/verify/remove verbs plus the registry surface — search, publish, and registry.list|get|add|remove — as an ndjson JSON-RPC service over stdio for agents and daemons that want a persistent handle instead of one-shot CLI calls. Registry name-or-ref resolution and config writes go through tamias-registry-open, the same code the CLI verbs use. The protocol is specified in serve reference.

A second embedding surface targets generated clients: tamias-driver-tamias exposes the engine's clap tree as a pavo ops manifest (cli.<verb> wire queries), so pavo's CLI/MCP renderers drive the same verbs without a hand-written client — see Scripting tamias.

Observability ​

tamias-telemetry is an opt-in OpenTelemetry layer over the tracing stack. Nothing exports unless you set an endpoint:

  • TAMIAS_OTEL_ENDPOINT — OTLP/HTTP base URL (the opt-in switch), or the standard OTEL_EXPORTER_OTLP_ENDPOINT / …_TRACES_ENDPOINT.
  • TAMIAS_OTEL_SERVICE_NAME / OTEL_SERVICE_NAME — service.name.
  • W3C traceparent/tracestate propagation is installed when export is on; RUST_LOG-style filtering still applies.

Where it sits ​

Tamias is the substrate of the delivery layer — everything above it is distributed through tamias:

delivery  →  memory  →  process  →  interface
tamias,      myco,      sturn,      pavo
scarab,      kuda,      cuora,
tarsi,                  mimus,
bupha,                 cicada,
hypha                   lasius,
                        sepia,
                        peregrin

An organism like myco ships its config as a myco-config pack; a campaign bundle ships as peregrin-bundle; a CI fleet ships as type: bupha. Tamias never learns what the bytes mean — the content type's driver does. See Content types.
