Architecture ​

Seeded from a copy of cuora (its ports-and-adapters anatomy and the -cf Worker pattern).

tamias is ports-and-adapters. The engine owns the generic half of distribution; every content meaning is an adapter.

The install path ​

ref ─► resolve ─► (cache hit?) ─► fetch ─► overlay (include:) ─► driver install ─► store

resolve pins git refs to a commit sha up front, so the content- addressed cache can be hit before fetching. The fetch→unpack split is what makes repeat installs and air-gapped nodes free.

Stores ​

  • install store — <name>@<version>/ with a record (source ref, resolved sha, payload digest, installed-at).
  • fetch cache — content-addressed; remove never touches it.
  • registry — where published content lives: a directory, or a Cloudflare Worker + R2 + D1/KV.

Provenance ​

verify recomputes the payload digest against the record. Digest-pinned refs (#sha256:…, resolved shas) are the integrity contract — see Security model for the full trust story, including the --allow-drivers consent gate on payload-shipped drivers.

The embedding surface ​

tamias serve (the tamias-serve crate) runs the same install/list/ info/verify/remove verbs as an ndjson JSON-RPC service over stdio — for agents and daemons that want a persistent handle instead of one-shot CLI calls. The protocol is specified in serve reference.

Observability ​

tamias-telemetry is an opt-in OpenTelemetry layer over the tracing stack. Nothing exports unless you set an endpoint:

  • TAMIAS_OTEL_ENDPOINT — OTLP/HTTP base URL (the opt-in switch), or the standard OTEL_EXPORTER_OTLP_ENDPOINT / …_TRACES_ENDPOINT.
  • TAMIAS_OTEL_SERVICE_NAME / OTEL_SERVICE_NAME — service.name.
  • W3C traceparent/tracestate propagation is installed when export is on; RUST_LOG-style filtering still applies.
