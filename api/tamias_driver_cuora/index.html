tamias-driver-cuora — the pavo view driver for cuora, plus the engine ops surface.

Verbs (the tamias driver contract):

  • manifest — print the [DriverManifest] JSON (discovery probe; never touches vault state).
  • capabilities — {"capabilities": ["pavo"], "verbs": […]}.
  • ops — the engine ops manifest: every bounded cuora CLI verb as a cli.<verb> wire query, derived from the engine’s own clap tree ([cuora::command]). Unbounded/stdin-bound verbs (serve, put, rotate) are surfaces, never ops.
  • run <argv> — engine passthrough: tamias-driver-cuora run list ≡ cuora list. Also the child side of cli.* wire queries (ops::run_verb re-execs this same verb so engine output never touches the serve stream).
  • cli <cuora argv> — the tamias bins[] shim verb: tamias bin exec calls it with the standard --dir/--name driver flags ahead of the user’s argv; they’re stripped and the rest runs through cuora::run_from in-process with inherited stdio — full engine parity (serve streams, put reads stdin, globals/--json/--version all work).
  • serve — ndjson JSON-RPC on stdio: {"op":"manifest"}, {"op":"views"}, {"op":"view","view":…,"params":{…}}, {"op":"query","query":…,"params":{…}} → {"ok":true,"result":…} / {"ok":false,"error":…}. query:"ops" answers the ops manifest; query:"cli.<verb>" runs the engine op.

Optional surfaces: feature mcp embeds pavo-driver-kit’s surface layer — mcp serves the ops manifest as MCP tools on stdio, equivalent to the standalone tamias-driver-mcp surface driver minus the PATH/discovery hop. (cli needs no feature: it’s the bins-shim passthrough above, not a generated surface — the engine’s own argv grammar is the contract.)

Target resolution: each view/query builds cuora_ops::Ops from the request params — config/env/actor map to the CLI’s --config/--env/--actor; absent params fall through to $CUORA_CONFIG → ./cuora.toml → ~/.config/cuora/cuora.toml, $CUORA_ENV, $CUORA_ACTOR/$USER — identical to cuora verbs. See data.rs for the secrets-safety contract: the view side renders vault metadata only, never values. Ops are the engine surface — get/env ops return values in captured stdout by design (the escape hatches); put/rotate/serve stay surfaces because they need stdin/never return.

ops 🔒
Engine ops — cli.<verb> wire queries dispatch into the cuora engine lib through this binary’s own run verb: each call re-execs tamias-driver-cuora run <argv> with the request’s params mapped to cuora’s globals, so cuora::dispatch writes to the child’s captured stdout and never touches the serve loop’s ndjson stream — and every mutation keeps the engine’s own semantics (config search, audit events, guardrails).
views 🔒
views — the driver’s manifest: every ViewSpec plus the wiring that turns query bindings into [ViewResult] data.
