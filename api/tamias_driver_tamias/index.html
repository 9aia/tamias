tamias-driver-tamias — the pavo view driver for tamias itself: the install store, fetch cache, registry index, and the tamias-driver-* driver dir, as declarative ViewNode views.

Verbs (the tamias driver contract):

  • manifest — print the [DriverManifest] JSON (discovery probe; never touches store state).
  • capabilities — {"capabilities": ["pavo"], "verbs": […], "types": []}. The empty types keeps tamias’s own capability-fallback driver lookup from claiming content types through this binary (its install verbs are pavo’s, not a content type’s).
  • serve — ndjson JSON-RPC on stdio: {"op":"manifest"}, {"op":"views"}, {"op":"view","view":…,"params":{…}}, {"op":"query","query":…,"params":{…}} → {"ok":true,"result":…} / {"ok":false,"error":…}.

Which tamias home: every view/query resolves its own roots — params.home/store/cache/registry/drivers → the same $TAMIAS_HOME/$TAMIAS_CACHE/$TAMIAS_REGISTRY/XDG chain the tamias CLI uses (see data.rs). manifest/views are root-free so pavo can enumerate drivers anywhere.

The driver is read-only: it walks <store>/…/.tamias-store.json records, counts cache entries, and scans the driver dir — the same reads tamias list/info/doctor do. tamias install/ remove/cache clean stay the write surface.

Note: the executable name tamias-driver-tamias is also what tamias’s content-driver host looks up for a content type named tamias — no such type exists today, and this driver’s capabilities claims no types, so only an explicit type: tamias package would ever route install verbs here (and they would fail loudly, not silently).
